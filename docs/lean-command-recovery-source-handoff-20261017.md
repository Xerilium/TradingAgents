## 1. Commands and baskets

- `tradingagents/web/admission.py`: durable account-wide block-new-orders, actor/reason history, separate paper-exercise grants bound to exact command IDs/terms/account/operations/expiry, revocation, exact submit/cancel/replace intents, and a versioned network-attempt boundary committed before I/O. Cancel authority is separate from the new-order block; replacement needs independently approved/admitted child terms. Unblocking creates or revives no grant.
- A never-dispatched resolution requires the versioned durable boundary to remain `not_started`. Broker identities, fills or native deliveries prevent submit no-send resolution. Started or legacy-unproven attempts remain uncertain. New submit attempts require renewed proposal approval; cancel/replace no-send does not infer the working order's broker state or release its original commitment.
- Basket freezing binds every current basket leg to its exact proposal revision, terms digest and unused approval. All legs reserve in one existing admission transaction against the same account's cash/shares/commitments. Dependencies reference preceding durable commands and require full authoritative fills plus current-worker native durability. No separate execution ledger or sale-proceeds credit was added.
- Basket execution plans retain command IDs, frozen legs, completion rows, actor/reason and review history. The investor can dispatch the next authorized leg, pause a plan, or review still-valid remaining authority. Rejected, expired, unknown, not-sent or invalidated legs require review; resume cannot revive invalid approvals. Plan revisions cannot duplicate an existing frozen revision.
- `tradingagents/web/approval_review.py`: an approval's own admitted command is excluded from its repeated hypothetical review, while other account commitments remain included.
- `tradingagents/web/policy_evaluation.py`: native-pending commitments remain visible and block readiness. Conservative adverse-loss and correlation inputs retain holdings whose sales may remain unfilled, including non-atomic basket cases. Explicit fee ceilings remain estimates, not invented actual commissions.
- `tradingagents/web/execution_lifecycle.py`: actual submit/cancel/replace paths cross the durable network boundary immediately before transport. A legitimate submit event is generated after that boundary; transport/mapping uncertainty retains commitments. Authoritative action outcomes close only the corresponding authorization. SELL recovery reservations retain fee commitments.
- `tradingagents/web/service.py`, `server.py`, `static/command-controls.js`: service routes and browser controls cover persistent blocking, scoped exercise authorization/revocation, exact command submit/cancel/replace, evidence-based no-send resolution, frozen basket admission, next-leg dispatch and pause/review.

`PAPER_WRITES_ENABLED` and the service transport gate remain false. Browse-only still rejects approval, exercise grants, admission and dispatch. Local blocking is available without equating it to cancellation or liquidation. No grant, admission or intent was created in runtime data.

## 3. Browser-operated paired recovery

- `tradingagents/web/paired_recovery.py`: paired backup/preview/restore/continuation/status through existing authenticated browser recovery routes. The pair binds installation, account, application identity, native configuration identity, namespace, exact closed cut and component checksums. Preview and commit reuse the application validator and native archive validator. An uploaded pair contains only fixed manifest/application/native members; it supplies no commands, credential paths, target paths or container names.
- Browser uploads are bounded to 64 MiB compressed, with bounded component/expanded/archive counts and the existing application evidence rules. Native RDB validation retains its existing 512 MiB limit. Paired backup creation rejects components outside its supported browser boundary rather than claiming they can be restored. Oversized or unsupported archives fail explicitly; original artifacts remain retained.
- Durable recovery stages distinguish retention, Redis stop, RDB staging, helper startup, AOF rebuild, helper removal, application generation selection, normal Redis startup and awaiting fresh reconciliation. Failure preserves its stage and original records; continuation revalidates the retained original upload and consumes checksum-bound components. Interrupted phase selection does not establish readiness.
- `tradingagents/web/native_persistence.py`: shared archive inspection, fixed existing-target container operations, backend-wide writer ownership plus retained namespace leases, and a backend restore marker. This detects older namespace-only writers and prevents another native worker using the RDB-only helper during recovery. The helper uses only the installed pinned image with no pull, exact loopback endpoint, reviewed mounts and server-owned name. Container identity/image/labels/mounts/state are checked. Prior Redis data, native cuts and prior offline-stage records are retained. Paired recovery leaves the backend blocked until AOF conversion, application selection and normal Redis startup have all reached the appropriate stage.
- `tradingagents/web/recovery.py`: restoring an older application snapshot retains later durable commands, approvals/revocations, basket linkage, command evidence and conservative commitments. Divergent snapshots require authoritative reconciliation. Restoring does not itself release admitted or uncertain reservations. Both per-order approvals and paper-exercise grants are invalidated; block-new-orders is restored true. A genuine current durable local no-send proof remains the separate release route. A snapshot-only not-started marker becomes restored-unproven because its capture can predate later I/O; only boundaries retained from current authority remain eligible for local no-send resolution.
- `tradingagents/web/recovery_mode.py`: the damaged-journal browser surface accepts paired preview/restore/continuation using only the configured native target. Original damaged application files remain untouched. Readable original command authority is retained independently of unrelated invalid journal content. A validated sibling generation can activate in the same web process, still browse-only with the native worker stopped.
- Unreadable authority or missing command receipts retain an explicit `authority_history_incomplete` gap. This gap survives subsequent restores and prevents admission/reconciliation readiness; absent broker orders or an investor assertion cannot erase possible later commitments. Readable historical records can be recovered for inspection without pretending missing authority was reconstructed.
- `service.py`, `server.py`, `nautilus_runtime.py`: normal writes and native startup are blocked during incomplete paired stages. After staging, only read-only startup/recovery/reconciliation actions and order blocking proceed until fresh native recovery completes. Browser Start Nautilus starts only the exact existing reviewed Redis container, then the configured worker; it does not provision or install a backend. A completed recovery becomes awaiting fresh reconciliation again after web restart.
- `static/paired-recovery.js`, `static/recovery.html`, `static/recovery.js`, `static/app.js`, `static/index.html`: health/settings and damaged-journal browser controls show exact manifests/checksums, retained originals, failed/incomplete phases and continuation. Broker outcomes and native durability stay separate. Normal Redis/SQLite recovery is explicitly non-atomic. Restored UI selections do not retain an exercise grant.
