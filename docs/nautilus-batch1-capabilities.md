### Native-process proof and retained outcomes

`nautilus_worker.main` generates one UUID for the actual worker/native-node process and exposes its PID and epoch in native snapshots. Reconstructing a web adapter object does not create or renew this identity. Reconnecting the client within the same retained native node keeps that identity. A new worker process creates a new one; this is not based on an OS PID that can be reused.

`ExecutionLifecycle` receives that worker identity. On a new native epoch, prior applied proofs become unresolved and retain their previous application history, immutable receipt reference, original event input and source digest. Broker command state, cumulative fills, receipts, fill IDs and commitments are not reset. Current native order identity plus a matching actual OrderFilled event's trade/venue/instrument/side/time/quantity/price/commission are required before a fill receipt is proven applied for this epoch. A conflicting or unproven existing native trade ID cannot be applied a second time. Same-process incoming duplicates also recheck the native cache. Restored/recovering receipts remain proof-only: no blind event replay beside imported exposure is enabled. Admission reconciliation rejects absent or mismatched native-process proof, including terminal commands with unresolved native deliveries.

Historical observations deduplicate equal fill identities for native report construction while retaining the complete original observation; conflicting identities block. Quantity totals must equal each parent order's actual cumulative filled quantity. Each observed fill is also projected with `native_application` proof against the actual current native order/event cache. A source fill not represented there is an explicit reconciliation gap, including any native filtering or dropped group; a source receipt alone is not reported as successful native application. This compares existing sources and cache, not a second ledger. The existing 24-hour / 1,000-fill / 500-open-order budgets are not extended and are not represented as full historical coverage. Exact zero commission is accepted only when present in the source; missing commission remains missing and blocks historical conversion.
